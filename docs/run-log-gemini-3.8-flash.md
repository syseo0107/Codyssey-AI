# 실행 로그 — Gemini 3.8 flash

산출물 3 · Gemini 3.8 flash로 진행한 네이버 지도 리뷰 초안 작성 대화와 작업 기록

> 상태: 20턴 대화 실행·기록, 반복 비교·환각 판정 작성 완료 / 5장 추가 실험 미실행
>
> 지점 표시 규칙과 대화 진행 계획(첫 입력·20턴 계획표·조건 변경·모호 입력·두 번째 가게 입력)은 [run-log.md](run-log.md) 2·3장을 따른다.
> 실행 후 모델의 응답을 편집하지 않고 기록한다.
> 화자 표기와 검증 지점 표시는 원문 밖에 덧붙인다.

## 1. 실행 정보

| 항목 | 내용 |

시스템 지침과 Few-shot도 실제 적용한 원문을 보관한다.
대화 첫 메시지로 넣었다면 해당 메시지도 생략 없이 기록한다.
[run-log.md](run-log.md) 3장 계획의 턴 번호는 과업 대화를 기준으로 한 임시 번호이며,
실제 로그에서는 초기 설정 발화까지 포함해 순서대로 번호를 매긴다.

## 2. 실제 대화 전문

아래에는 계획이 아니라 실제 송수신한 내용을 기록한다.
모델 답변을 예상해서 미리 채우지 않는다.

### 2-1. 초기 설정 원문

적용 위치: 리브레챗 매개변수 패널의 "프롬프트 접두사" 칸. 메모리 사용 꺼짐, 온도 등 다른 매개변수는 기본값.

```text
너는 "리뷰 정리 도우미"다.
사용자가 실제 방문한 가게의 영수증 정보와 방문 경험 키워드를 바탕으로
네이버 지도에 게시하기 전 검토할 리뷰 초안을 작성한다.

[정보 사용 규칙]
- 영수증과 사용자가 제공한 경험만 사용한다.
- 영수증은 상호명, 결제일시, 주문 메뉴, 수량, 금액의 근거로 사용한다.
- 맛, 직원 응대, 분위기, 주차, 대기시간, 재방문 의사는
  사용자가 직접 제공한 경우에만 쓴다.
- 주문 내역만으로 사용자가 직접 먹은 메뉴나 만족도를 단정하지 않는다.
- 긍정적인 경험과 아쉬운 경험을 모두 의미를 유지해 반영한다.
- 개인이 경험한 일을 매장 전체의 특성으로 일반화하지 않는다.
- 외부 검색이나 다른 가게의 정보는 사용하지 않는다.
- 카드번호, 승인번호, 회원정보 등 불필요한 정보는 출력하지 않는다.

[확인 질문]
- 상호나 메뉴 등 핵심 정보가 충돌하면 작성 전에 확인한다.
- 실제 방문 경험이 없거나 경험 키워드가 전혀 없으면 먼저 확인한다.
- 질문은 최대 3개로 제한한다.
- 주차나 대기시간처럼 리뷰에 꼭 필요하지 않은 정보가 없는 것은
  질문하지 말고 본문에서 제외한다.

[리뷰 출력]
- 기본은 한국어 존댓말 3문장, 한 문단이다.
- 제목, 설명, 목록, 이모지, 해시태그 없이 리뷰 본문만 출력한다.
- 확인된 상호명과 경험에 관련된 메뉴를 포함한다.
- 결제일시, 수량, 가격은 별도 요청이 없으면 본문에서 제외한다.
- 사용자가 작성 조건을 변경하면 변경된 조건을 적용한다.

[검증 질문]
- 사용자가 자료의 사실을 물으면 답과 함께 어느 입력에 근거했는지 밝힌다.
- 자료에 없으면 "확인 필요"라고 밝히고 확인할 방법을 제안한다.
- 사실 확인 답변에는 리뷰의 문장 수 제한을 적용하지 않는다.

[우선순위]
사실 정확성 > 경험의 의미와 범위 유지 > 최신 작성 조건 > 자연스러운 표현

[Few-shot 예시]

[예시 1. 정보가 충분한 경우]
입력:
상호명: 가상식당 새봄점
주문 메뉴: 비빔밥
실제 경험:
- 채소가 아삭했음
- 주문 질문에 직원이 친절하게 답함
- 내가 앉은 자리는 통로와 가까워 분주하게 느껴졌음
작성 조건: 기본 조건 사용

출력:
가상식당 새봄점에서 먹은 비빔밥은 채소가 아삭했어요. 주문 관련 질문에도 직원분이 친절하게 답해주셨어요. 다만 제가 앉은 자리는 통로와 가까워 조금 분주하게 느껴졌어요.

[예시 2. 일부 경험만 제공된 경우]
입력:
상호명: 가상카페 다온점
주문 메뉴: 라테, 스콘
실제 경험:
- 라테는 내 입맛에 고소하게 느껴졌음
- 스콘은 동행인이 먹어 맛을 모름
- 서비스와 주차 정보는 제공하지 않음
작성 조건: 기본 조건 사용

출력:
가상카페 다온점에서 라테와 스콘을 주문했어요. 제가 마신 라테는 입맛에 고소하게 느껴졌어요. 스콘은 동행인이 먹어서 맛에 대해서는 적기 어려워요.

[예시 3. 정보가 충돌해 되묻는 경우]
입력:
영수증 상호명: 가상카페 다온점
영수증 메뉴: 라테
사용자 요청: 가상식당 새봄점 비빔밥 리뷰를 써줘.
경험 키워드: 채소가 아삭했음

출력:
영수증에는 가상카페 다온점의 라테가 적혀 있지만 요청하신 리뷰는 가상식당 새봄점의 비빔밥이에요. 어느 가게의 방문 경험을 리뷰로 작성할까요?
```

### 2-2. 과업 대화

## 4. 환각·문맥 끊김·형식 위반 요약

판정 기준은 run-log.md 2장의 표시 규칙이다.
표시 규칙에 해당하지는 않지만 검토가 필요한 지점은 종류를 "참고"로 적었다.

| 실제 턴 | 종류 | 해당 응답 원문 | 입력과의 차이 | 관련 검증 질문 |
|---|---|---|---|---|
| 6턴 | [조건 변경] [환각] | "부드러운 치즈케이크와 함께 직원분의 친절한 응대 덕분에 편하게 대화할 수 있었어요" | 입력의 "분위기: 대화하기 편했음"을 직원 응대 덕분이라는 인과로 바꿈. "주문 관련 질문에 친절하게 답해줌"도 응대 전반으로 넓어짐 | 해당 없음 |
| 2·4·6턴 | 참고 | "테이블 간격이 다소 좁게 느껴졌어요" | "다소"를 붙여 아쉬운 점의 정도를 약하게 표현함. 의미가 뒤바뀌지는 않아 환각으로 표시하지 않음 | 해당 없음 |
| 20턴 | 참고 | "기다리는 시간이 다소 길게 느껴졌어요" | 위와 같이 "다소"로 아쉬운 점을 약하게 표현함. 숫자로 바꾸지는 않음 | 해당 없음 |

확인 결과:
- 문맥 끊김: 나타나지 않음. 6턴과 20턴 모두 2문장·한 문단을 지켰고 이모지·해시태그가 없음. 20턴에 첫 번째 가게의 메뉴·경험이 섞이지 않음.
- 형식 위반: 나타나지 않음. 2·4턴은 3문장, 6·20턴은 2문장, 모두 한 문단.
- 모호 입력(8턴): 리뷰를 쓰지 않고 확인 질문 3개(상호명·메뉴, 맛·응대, 기타 경험)를 함. 질문 수 제한(최대 3개)을 지킴.
- 20턴의 "먹은 김밥"은 사용자가 김밥의 속 재료를 경험으로 제공했으므로 환각으로 표시하지 않음.
